# NEXO on AWS

**[English](INSTALL.md) · [Español](INSTALL.es.md)**

Prepares an EC2 instance for a personal NEXO deployment. The instance
runs the API as a host service because the extractor sandbox needs to
invoke Docker with explicit limits. PostgreSQL and the objects are kept
on persistent storage under the instance's own control.

This guide and `provision.sh` cover everything that doesn't touch the
AWS account itself (packages, database, binary, service). Creating the
EC2 instance, the security group, and the elastic IP is a separate step,
deliberately left outside this script — those are billed account
resources, and that decision belongs to whoever pays for them, not to a
script.

## 0. Create the instance (outside this repo)

Amazon Linux 2023, a `t3.small` is enough to start (2 vCPU, 2 GiB — scale
up if evidence volume justifies it), persistent EBS storage (20 GiB
minimum), and a security group allowing:

- 22/tcp (SSH) from your IP only.
- 443/tcp (HTTPS) from anywhere — the only thing meant to be public.
- 80/tcp (HTTP) from anywhere — only for the Let's Encrypt ACME
  challenge.

## 1. Provision the host

### 1.0 Connect to the server (two ways)

**Without a `.pem` file — recommended if you don't have it handy or
don't know what it is:** AWS lets you connect through the browser, with
no key installed on your own computer.

1. Go to [console.aws.amazon.com](https://console.aws.amazon.com) with
   the account that created the instance.
2. EC2 → Instances (check you're in the right region — this project
   uses `us-east-2`).
3. Click the NEXO instance → **"Connect"** button (top right).
4. **"EC2 Instance Connect"** tab → **Connect** button.
5. A terminal opens in the browser, already connected to the server.
   You're ready to continue with the commands below.

If that tab doesn't show up or fails (depends on the security group's
network configuration), use the traditional way:

**With a `.pem` file** — the private key downloaded once, when the EC2
instance was created:

```sh
ssh -i <path-to-your-key.pem> ubuntu@<instance-IP-or-domain>
```

If `ubuntu@` fails with a user error, try `ec2-user@`. If you lost the
`.pem` file, it cannot be re-downloaded — that's exactly what the
no-`.pem` method above is for.

### 1.1 Run the provisioning

With the instance running and connected (by either method above):

```sh
git clone https://github.com/annatchijova/nexo.git
cd nexo
sudo ./deploy/aws/provision.sh
```

`provision.sh` is idempotent — it installs Docker and PostgreSQL 16,
creates the `nexo` system user, the `nexo` role and database in
Postgres, builds the three sandboxed extractors
(`scripts/build_extractors.sh`) and the `nexo-api` release binary,
writes `/etc/nexo/nexo-api.env` (only if it doesn't already exist — it
never overwrites secrets already generated), and installs and starts
`deploy/aws/nexo-api.service`.

The first run generates `NEXO_BOOTSTRAP_OWNER` — the bearer token for
the instance's sole owner. The variable lives in the protected file
`/etc/nexo/nexo-api.env`; the administrator must retrieve it on the
server and hand it over through a private channel:

```sh
sudo awk -F= '$1=="NEXO_BOOTSTRAP_OWNER"{print $2}' /etc/nexo/nexo-api.env
```

Store it in a password manager. Never paste it into Git, public
documentation, screenshots, or open chats. If it's lost, the database
cannot reconstruct it — it only keeps a hash — a new credential has to
be issued through an authenticated or controlled flow.

**Known limitation, not an oversight:** this is currently the only
mechanism for granting access — there is no invite flow or self-service
signup inside the app. Provisioning the server and granting a person
access are, for now, the same manual SSH step. That's real friction for
anyone who isn't a systems administrator, and it's noted as the next
step in [`docs/KNOWN_LIMITATIONS.md`](docs/KNOWN_LIMITATIONS.md), not
hidden.

## 2. Variables in `/etc/nexo/nexo-api.env` (permissions `0600`)

`provision.sh` already writes these; this is a reference for what each
one does:

```text
DATABASE_URL=postgres://nexo:<password>@127.0.0.1:5432/nexo
NEXO_BOOTSTRAP_OWNER=<long token, generated by provision.sh>
NEXO_OBJECT_STORE_ROOT=/var/lib/nexo/objects
NEXO_EXPORT_ROOT=/var/lib/nexo/exports
NEXO_BIND_ADDR=127.0.0.1:8080
NEXO_WEB_ORIGIN=https://nexo-web-sigma.vercel.app
NEXO_AUDIT_HMAC_KEY=<long key, generated by provision.sh>
NEXO_AUDIT_HMAC_KEY_VERSION=v1
```

`NEXO_AUDIT_HMAC_KEY` and `NEXO_AUDIT_HMAC_KEY_VERSION` are mandatory,
not optional: `nexo_app::audit::append` (the path that logs every
mutation — evidence, assertions, evaluations, preparations, credentials)
requires them and fails without them, so **without these two variables
the API rejects every write**, not just one audit-specific feature.
`NEXO_AUDIT_HMAC_KEY_VERSION` can stay `v1` indefinitely on a
single-operator instance; it only needs to increment if you ever rotate
the key.

None of these values should ever show up in logs, saved commands, Git,
or public documentation.

## 3. TLS

`nexo-api` only listens on `127.0.0.1:8080` — nothing exposes that to
the network directly. `deploy/aws/Caddyfile` puts Caddy in front as the
TLS terminator, with automatic Let's Encrypt renewal (no manual certbot
step).

The `@caddy/caddy` COPR repository **does not publish a build for Amazon
Linux 2023** (only Fedora/EPEL/openSUSE) — confirmed by trying it on a
real deployment, not assumed. Installing the official binary directly is
the path that actually works:

```sh
CADDY_VERSION=$(curl -s https://api.github.com/repos/caddyserver/caddy/releases/latest | grep -o '"tag_name": *"[^"]*"' | cut -d'"' -f4)
curl -sL -o /tmp/caddy.tar.gz "https://github.com/caddyserver/caddy/releases/download/${CADDY_VERSION}/caddy_${CADDY_VERSION#v}_linux_amd64.tar.gz"
tar xzf /tmp/caddy.tar.gz -C /tmp caddy
sudo install -m 0755 /tmp/caddy /usr/local/bin/caddy

sudo mkdir -p /etc/caddy /var/log/caddy /var/lib/caddy
sudo id caddy >/dev/null 2>&1 || sudo useradd --system --home /var/lib/caddy --shell /sbin/nologin caddy
sudo chown -R caddy:caddy /var/lib/caddy /var/log/caddy

# edit deploy/aws/Caddyfile: replace api.example.com with your real domain
# (or, without your own domain, "<ip-with-dashes>.sslip.io" — see note below)
sudo install -m 0644 deploy/aws/Caddyfile /etc/caddy/Caddyfile
sudo install -m 0644 deploy/aws/caddy.service /etc/systemd/system/caddy.service
sudo systemctl daemon-reload
sudo systemctl enable --now caddy
```

You need a real DNS name pointing at the instance's IP before this step
— Caddy can't issue a valid certificate for a bare IP. If you don't have
your own domain yet, [sslip.io](https://sslip.io) resolves
`<ip-with-dashes>.sslip.io` to that IP automatically with no prior
registration (for example, IP `3.150.146.250` is
`3-150-146-250.sslip.io`) — it's real public DNS, so Let's Encrypt
validates it just like a real domain. Once you get your own domain, it's
a one-line change in the Caddyfile plus a reload
(`sudo systemctl reload caddy`).

## 4. Connect the frontend

Configure `VITE_NEXO_API_BASE` in Vercel with the HTTPS URL from the
previous step (`https://your-domain`, or
`https://<ip-with-dashes>.sslip.io`).

## 5. Verify before using real evidence

```sh
curl -s https://your-domain/healthz
```

Then, from the UI (or with `curl`, see `docs/API_CONTRACT.md`): create a
case, add evidence of all three types (`plain_text`, `eml`, `pdf`),
evaluate, prepare (`draft_request` and `evidence_package`), export, and
verify the export independently with `nexo-verify`. This full sequence,
including the public HTTPS path through Caddy (not just against
`127.0.0.1`), was run against a real EC2 instance (Amazon Linux 2023,
`t3.small`) provisioned with this same `provision.sh` — see the
"Status" section of the [Technical README](docs/TECHNICAL_README.md)
for the exact detail of what was verified, when, and the three real
deploy bugs that run found and that `provision.sh` already has fixed
(missing musl target, insufficient swap on `t3.small`, Postgres `ident`
authentication).

## Backups

Not automated yet by `provision.sh`. At minimum: periodic `pg_dump` of
the `nexo` database and a copy of `/var/lib/nexo/objects` and
`/var/lib/nexo/exports` (they hold the original evidence bytes — losing
them without warning is not acceptable for what this project sets out to
preserve). EBS snapshots are the simplest option if the whole volume is
under `/var/lib/nexo`.
